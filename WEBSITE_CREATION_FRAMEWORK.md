# 2. Перед созданием любого нового сайта

До написания кода нужно зафиксировать четыре решения.

## 2.1. Локальная папка

Нужно определить точный путь, где проект будет жить на компьютере.

Рекомендуемая общая структура:

```text
C:\Users\nikek\Projects\<project-name>
```

Если новый сайт связан с уже существующим проектом, лучше создать его рядом с ним, а не в случайной папке.

Путь должен быть подтверждён до начала разработки.

## 2.2. Нужны ли сайту данные

Нужно определить один из вариантов:

### Вариант A — полностью статический сайт

Подходит для:

- лендингов;
- портфолио;
- инструкций;
- справочных страниц;
- сайтов без редактируемых пользовательских данных.

Архитектура:

```text
HTML + CSS + JavaScript
→ публичный GitHub-репозиторий
→ GitHub Pages
```

База данных не нужна.

### Вариант B — данные только в одном браузере

Подходит для прототипа или личного инструмента на одном устройстве.

Хранение:

- `localStorage`;
- IndexedDB.

Ограничение: данные не синхронизируются между телефоном и компьютером.

### Вариант C — приватные данные между устройствами

Подходит для планеров, журналов, финансовых инструментов и других персональных приложений.

Рекомендуемая архитектура:

```text
Публичный frontend-репозиторий
+
Приватный data-репозиторий или настоящая база данных
+
Проверенная граница авторизации/API
```

Frontend не должен содержать:

- GitHub-токены;
- API-ключи;
- пароли;
- приватные записи;
- экспортированные пользовательские данные.

## 2.3. GitHub-репозитории

Перед удалёнными действиями необходимо определить:

1. название frontend-репозитория;
2. public или private;
3. нужен ли отдельный data-репозиторий;
4. public или private для data-репозитория;
5. подтверждена ли публикация через GitHub Pages.

## 2.4. Адрес сайта

Для обычного GitHub Pages проекта адрес будет:

```text
https://<github-username>.github.io/<repository-name>/
```

Например:

```text
https://kupalsa.github.io/kupalsa-planner/
```

# 3. Рекомендуемая структура файлов проекта

Для простого статического сайта:

```text
project-name/
├── index.html
├── assets/
│   ├── images/
│   ├── icons/
│   └── fonts/
├── css/
│   └── styles.css          # если CSS вынесен из index.html
├── js/
│   └── app.js              # если JavaScript вынесен из index.html
├── tests/
│   └── app.test.js
├── .github/
│   └── workflows/
│       └── deploy-pages.yml
├── .gitignore
├── .nojekyll
├── README.md
└── WEBSITE_CREATION_FRAMEWORK.md
```

Для небольшого автономного инструмента допустим один `index.html`, если это реально упрощает поддержку.

Для приложения с приватными данными:

```text
frontend-repo/
├── index.html
├── assets/
├── tests/
├── .github/workflows/deploy-pages.yml
├── .gitignore
└── README.md

private-data-repo/
└── data/
    ├── index.json
    └── records/
        └── <record-id>.json
```

# 4. Пошаговое создание локального проекта

## Шаг 1 — создать папку

Пример для Git Bash:

```bash
mkdir -p "C:/Users/nikek/Projects/my-site"
cd "C:/Users/nikek/Projects/my-site"
```

## Шаг 2 — создать минимальный сайт

Минимальный `index.html`:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>My Site</title>
</head>
<body>
  <main>
    <h1>My Site</h1>
  </main>
</body>
</html>
```

Требования:

- должен присутствовать viewport для телефонов;
- страница должна работать без локальных абсолютных путей;
- ссылки на файлы должны быть относительными;
- секретов в коде быть не должно.

## Шаг 3 — добавить `.gitignore`

Пример:

```gitignore
.env
.env.*
node_modules/
dist/
coverage/
*.log
.DS_Store
Thumbs.db
private-data/
exports/
```

Если используются дополнительные инструменты, список расширяется.

## Шаг 4 — добавить `.nojekyll`

Пустой файл `.nojekyll` сообщает GitHub Pages, что проект нужно отдавать как обычный статический сайт без обработки Jekyll.

## Шаг 5 — добавить README

README должен содержать:

- назначение сайта;
- локальный путь проекта;
- технологию;
- команду локального запуска;
- ссылку на опубликованный сайт;
- описание хранения данных;
- инструкции проверки и публикации.

# 5. Как открыть и проверить сайт локально

Не нужно открывать `index.html` двойным кликом, если JavaScript использует `fetch`, модули или другие браузерные API. Надёжнее запускать локальный HTTP-сервер.

## Python HTTP server

Из папки проекта:

```bash
python3 -m http.server 8765
```

Открыть:

```text
http://127.0.0.1:8765/
```

Остановить сервер:

```text
Ctrl+C
```

## Что проверять локально

- страница загружается без ошибок;
- все кнопки нажимаются;
- формы сохраняют данные;
- переходы работают;
- после обновления страницы состояние сохраняется ожидаемым способом;
- нет ошибок JavaScript в консоли;
- нет горизонтального скролла на телефоне;
- элементы не перекрывают друг друга;
- текст и кнопки имеют достаточный контраст;
- интерактивные элементы доступны с клавиатуры.

## Рекомендуемые размеры проверки

```text
Mobile:  390 × 844
Small:   320 × 700
Tablet:  768 × 1024
Desktop: 1440 × 900
```

# 6. Тестирование перед публикацией

Минимальная последовательность:

1. проверить синтаксис HTML и JavaScript;
2. запустить автоматические тесты;
3. открыть сайт локально;
4. проверить мобильную версию;
5. проверить desktop-версию;
6. проверить сохранение/загрузку данных;
7. убедиться, что секреты не попали в Git;
8. изучить `git diff` перед коммитом.

Пример запуска Node-тестов:

```bash
for file in tests/*.test.js; do
  node "$file" || exit 1
done
```

Проверка состояния Git:

```bash
git status --short
git diff
```

Поиск потенциальных секретов должен выполняться до публикации. Нельзя коммитить `.env`, токены или приватные JSON-данные.

В папке нового проекта:

```bash
git init

Проверить:

git log -1 --oneline
```

Рабочая директория после коммита должна быть чистой, кроме намеренно неотслеживаемых локальных файлов.

# 8. Создание репозитория GitHub

## Вариант с GitHub CLI

Если `gh` установлен и авторизован:

```bash
gh auth status
gh repo create my-site --public --source . --remote origin --push
```

Для private-репозитория:

```bash
gh repo create my-site --private --source . --remote origin --push
```

## Вариант через GitHub в браузере

1. открыть GitHub;
2. создать новый репозиторий;
3. выбрать имя и видимость;
4. не добавлять конфликтующий README, если локальный репозиторий уже содержит коммиты;
5. добавить remote локально;
6. отправить ветку `main`.

```bash
git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main
```

## Проверка remote

```bash
git remote -v
git branch --show-current
git status --short --branch
```

# 9. Настройка GitHub Pages

Есть два рекомендуемых варианта.

## Вариант A — публикация напрямую из ветки

Подходит для сайта без сборки.

В GitHub:

```text
Repository → Settings → Pages
→ Source: Deploy from a branch
→ Branch: main
→ Folder: /(root)
→ Save
```

После этого GitHub публикует `index.html` из корня ветки `main`.

## Вариант B — GitHub Actions

Подходит для более надёжного и воспроизводимого процесса.

Файл:

```text
.github/workflows/deploy-pages.yml
```

Пример workflow:

```yaml
name: Deploy static site to GitHub Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .
      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
```

В настройках Pages выбрать:

```text
Source: GitHub Actions
```

# 10. Обычный цикл обновления сайта

После изменения файлов:

```bash
cd "C:/Users/nikek/Projects/my-site"
```

## 1. Проверить изменения

```bash
git status --short
git diff
```

## 2. Запустить тесты

```bash
for file in tests/*.test.js; do
  node "$file" || exit 1
done
```

Также вручную проверить сайт локально.

## 3. Создать коммит

```bash
git add index.html css/ js/ tests/
git commit -m "Describe the website change"
```

Не использовать `git add .` вслепую в проектах с приватными данными.

## 4. Синхронизироваться с GitHub

```bash
git fetch origin
git status --short --branch
```

Если удалённая ветка содержит новые изменения, сначала безопасно интегрировать их:

```bash
git pull --rebase origin main
```

После разрешения возможных конфликтов снова запустить тесты.

## 5. Отправить изменения

```bash
git push origin main
```

Не использовать `--force` без ясного понимания, почему необходимо переписать удалённую историю. Для защищённого исключительного случая допустим только `--force-with-lease` после `git fetch` и явного подтверждения.

# 11. Проверка публикации

После push нельзя сразу считать сайт опубликованным.

Нужно проверить:

1. GitHub получил новый commit;
2. workflow GitHub Pages завершился успешно;
3. опубликованный HTML содержит новую версию;
4. публичный URL возвращает HTTP 200;
5. интерфейс действительно работает в браузере.

## Через GitHub

```text
Repository → Actions → последний Deploy workflow
```

Статус должен быть зелёным.

## Через браузер или curl

```bash
curl -I https://<username>.github.io/<repo>/
```

Ожидается:

```text
HTTP/2 200
```

Чтобы обойти старый браузерный кэш при проверке:

```text
https://<username>.github.io/<repo>/?v=<commit-sha>
```

После проверки удалить тестовый query-параметр необязательно — он не изменяет сайт.

# 12. Проверка в разных браузерах

Минимально проверить:

- Chrome desktop;
- Safari на iPhone;
- Chrome или Edge на Windows;
- узкий мобильный viewport.

Проверить:

- загрузку страницы;
- меню;
- все основные кнопки;
- формы;
- навигацию назад;
- обновление страницы;
- сохранение состояния;
- touch targets;
- отсутствие обрезанного текста;
- отсутствие перекрывающихся меню;
- корректную работу date/time inputs.

Если Safari показывает старую версию:

1. обновить страницу;
2. закрыть и открыть вкладку;
3. открыть URL с `?v=<commit-sha>`;
4. при необходимости очистить данные сайта — только если это не удалит важное локальное состояние.

# 13. Правила для сайтов с приватными данными

## Никогда не делать

- не вставлять токен в `index.html`;
- не коммитить `.env`;
- не хранить приватные записи в публичном репозитории;
- не выводить токен в консоль или логи;
- не добавлять тестовые персональные данные в frontend;
- не называть приложение синхронизируемым, если данные живут только в `localStorage`.

## Надёжное разделение

```text
Public frontend:
- HTML/CSS/JS
- публичные изображения
- тесты без приватных данных

Private data repository:
- пользовательские JSON-записи
- индексы данных
- приватные вложения

Browser-local storage:
- настройки подключения
- токен, если пользователь явно выбрал такую архитектуру
```

Для более критичных данных лучше использовать серверный API или Worker, чтобы токен вообще не попадал в браузерное приложение.

# 14. Рекомендуемый порядок работы ИИ-агента

Когда ИИ создаёт или обновляет сайт, он должен действовать в такой последовательности:

1. подтвердить локальную папку;
2. подтвердить необходимость базы данных и межустройственной синхронизации;
3. подтвердить frontend/data репозитории и их видимость;
4. изучить существующий код и инструкции проекта;
5. зафиксировать требуемое поведение;
6. написать тест, который сначала падает;
7. реализовать минимальное исправление;
8. запустить тест;
9. проверить весь актуальный набор тестов;
10. проверить JavaScript-синтаксис;
11. запустить сайт локально;
12. проверить mobile и desktop визуально;
13. проверить приватность и отсутствие секретов;
14. изучить `git diff`;
15. создать понятный commit;
16. получить/использовать явное разрешение на публикацию;
17. выполнить `git push origin main`;
18. проверить GitHub Actions;
19. открыть публичный URL;
20. подтвердить реальный результат, а не только наличие коммита.

# 16. Короткая формула процесса

```text
Подтвердить папку и данные
→ создать локальную структуру
→ написать и протестировать сайт
→ инициализировать Git
→ создать GitHub-репозиторий
→ настроить GitHub Pages
→ push в main
→ дождаться deploy
→ проверить публичный URL на desktop и mobile
```

Итог считается достигнутым только тогда, когда существуют одновременно:

1. рабочая локальная копия;
2. актуальный GitHub-репозиторий;
3. успешный GitHub Pages deployment;
4. публичный URL, открывающийся в обычном браузере;
5. подтверждённая проверка основных функций и адаптивного интерфейса.
